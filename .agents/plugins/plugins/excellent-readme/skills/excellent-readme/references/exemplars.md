# Reference READMEs

Rules describe what a good README contains; they do not convey tone, density, or rhythm. Read one or two of these when you need a concrete sense of how a well-regarded README actually reads.

> [!NOTE]
> These are external files that can change or disappear. They are calibration material, not a source of facts. If a link is unreachable, skip it and continue — never block the task on fetching one, and never cite one without having read it.

## Larger sample applications

Useful when the project is a service, a full-stack product, or anything with a deployment story. Observe how architecture and infrastructure detail stays below the quick start, and how much of the page is spent on getting the reader to a running system.

- <https://raw.githubusercontent.com/Azure-Samples/serverless-chat-langchainjs/refs/heads/main/README.md>

## Small focused tools

Useful when the project is a CLI, a library, or a single-purpose utility. Observe how short a complete README can be, how quickly the first runnable example arrives, and what the author chose to leave out.

- <https://raw.githubusercontent.com/sinedied/run-on-output/refs/heads/main/README.md>
- <https://raw.githubusercontent.com/sinedied/smoke/refs/heads/main/README.md>

## What to take from them

- The opening lines commit to a concrete purpose instead of a slogan.
- A copyable example appears before any discussion of internals.
- Formatting is plain: headings, code blocks, and occasional admonitions, not decoration.
- Length matches the project. Match the exemplar whose scale resembles the repository you are documenting, not the longest one.

## What not to take from them

- Their section list. Sections come from evidence in the target repository.
- Their badges, hosting choices, or vendor-specific deployment blocks.
- Their voice, if the user asked for a different language or register.
